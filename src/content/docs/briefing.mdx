Its built-in MCP server lets an AI agent run comparisons by itself. The lesson behind everything else: an agent is only as good as the facts you hand it.

<div class="b-journey"><span>Came from</span><span class="on">Now</span><span>Going</span></div>

<div class="b-tiles">
<div><strong>Actor Corroboration Grid <Badge kind="working" /></strong>A result counts only when independent actors agree</div>

<div><strong>One deterministic clock <Badge kind="working" /></strong>12 FPS, paired with NI I/O Trace and DETT</div>
<div><strong>Mark the spot <Badge kind="progress" /></strong>You mark where it went wrong; an agent explains that range</div>
</div>

<p class="b-banner">Break glass in case of emergency: the evidence is already captured</p>

<Notes>

This is where we are now: the [LabVIEW Benchmark Actor](https://github.com/svelderrainruiz/labview-benchmark-actor), built for the LabVIEW CI/CD community. Every machine with the extension is an actor with an abstract name, and there is no central results database. It does four things for me. A result counts only when independent actors in different environments agree. I capture LabVIEW launches so a tester can cover specific icon-editor CAR tests (a CAR is NI's bug-report number). Capture is frame-locked at 12 frames per second, so timings pair with NI I/O Trace and the Desktop Execution Trace Toolkit. And, in progress, you mark the spot where something went wrong, and an agent with no other context explains it. When something breaks, the evidence is already there. The next two slides open up the grid and the markers.

</Notes>

## Actor Corroboration Grid: agreement before trust

<div class="b-journey"><span>Came from</span><span class="on">Now</span><span>Going</span></div>

<div class="b-flow">
<div>Independent actors<small>different environments: Linux · Linux&nbsp;VM · Windows</small></div>
<div>Same anchors?<small>series hash · bus version · gate verdict</small></div>
<div class="b-hi">At least 2 of 3 agree<small>the release passes; if not, it is blocked and a divergence issue opens</small></div>
</div>

<p class="b-banner">Proven today: 2 benchmarks across 4 planes, 0 determinism violations</p>

<p class="b-foot">Each actor: your own golden VM (Ubuntu 24.04 + LabVIEW 2026 Community Edition) · a signed receipt · 13 MCP tools for agents · LBA-REQ-023, Proven</p>

<Notes>

The Actor Corroboration Grid is how a result earns trust. Independent actors in different environments, for example Linux, a Linux VM and Windows, re-run the same deterministic checks and each signs a receipt. Their anchors must agree: the series hash, the coordination-bus version and the gate verdict. If at least two of three agree, the release passes; if not, it's blocked and a divergence issue opens. There's no central results database: the receipts are the result. The cross-plane grid has two benchmarks proven across four planes with zero determinism violations, and the grid itself is a proven requirement.

</Notes>

## Markers: a human points, the agent explains

<div class="b-journey"><span>Came from</span><span class="on">Now</span><span>Going</span></div>

<div class="b-flow">
<div>A human marks the spot<small>two markers on the benchmark, where something looked wrong</small></div>
<div>An agent with no context<small>reads CPU · GPU · RAM · disk · screen in exactly that range</small></div>
<div class="b-hi">Hybrid verification<small>human judgement + agent speed: faster troubleshooting</small></div>
</div>

<div class="b-tiles b-three">
<div><strong>Data tagging</strong>What happened, labelled for later queries</div>
<div><strong>Video</strong>An animated clip of exactly that range</div>
<div><strong>Agentic docs</strong>Local agents update the documentation from the tagged facts</div>
</div>

<p class="b-banner">A marker hands the human's context to an agent that has none</p>

<p class="b-foot"><Badge kind="progress" /> Specified as LBA-REQ-105 · Planned until a gate proves it</p>

<Notes>

This is what makes it a hybrid. A human watching a benchmark knows where something looked wrong; an agent starts with no context at all. The marker is the hand-off: the human places two markers on the benchmark, and that range is all the context the agent needs. A local model then reads exactly that range (CPU, GPU, RAM, disk and the screen, on one clock) and explains what happened. Human judgement says where to look; the agent brings speed and evidence. That makes troubleshooting faster, and it turns verification and validation into an AI/human hybrid method. The tagged range then becomes a data tag for later queries, an animated clip of exactly that range, and documentation that local agents update from the facts. Screen frames stay on the machine that captured them; only metadata goes to the agent. It's in progress, specified as requirement 105, and stays planned until a gate proves it.

</Notes>

## From specification to verified results

<div class="b-journey"><span>Came from</span><span>Now</span><span class="on">Going</span></div>

<div class="b-chain">
<div>System requirements<small>SyRS: what the system must do</small></div>
<div>Software requirements<small>SRS: what each tool must do</small></div>
<div>Tests<small>prove each requirement</small></div>
<div>Decisions<small>record why</small></div>
<div>Results<small>receipts you can reproduce</small></div>
</div>

<p class="b-banner">Vibe-codeable: the spec tells your agent how, and the tests show it works</p>

<p class="b-foot">Example: the installer's published specification has 102 requirements and 58 test items · we compare requirements, not source</p>

<Notes>

Where we're going rests on one idea: vibe-codeable source. If you like something, you shouldn't have to reverse-engineer it: the specification tells your agent how to build it, and the tests show what it does. System requirements break down into software requirements, each traced to a test and a design decision, and every link is checked automatically. The installer's [published specification](https://github.com/svelderrainruiz/ecosystem/wiki/Software-Requirements-Specification), for example, has 102 requirements and 58 test items. That's why we compare requirements, not source, and it's what makes spec-driven collaboration scale.

</Notes>

## Security by governance, decisions by facts

<div class="b-journey"><span>Came from</span><span>Now</span><span class="on">Going</span></div>

<div class="b-cols">
<div class="b-box">

**Governance**

- Fail-closed gates before every merge (180+ in the Benchmark Actor)
- Independent review; every requirement traced to a test

</div>
<div class="b-box">

**Facts**

- Every session logs tokens, cost and operator time
- So a change can be priced before it is made

</div>
</div>

<Notes>

Two things make AI-assisted benchmarking robust. Governance: every change passes fail-closed gates before it's merged (the Benchmark Actor alone has more than 180), with independent review and every requirement traced to a test; this site deploys only if its own check passes. And facts: every working session records its AI tokens, cost and operator time in a database I own. That lets me say "this change will cost X if you do it this way", and hand documentation upkeep to local AI based on facts, not guesses.

</Notes>
