## Why: every tool was built to serve a real goal

<div class="from">Manual LabVIEW testing</div><div class="arrow">→</div><div class="to">Benchmarks an agent can run and verify</div>

<div class="from">My own source, without requirements</div><div class="arrow">→</div><div class="to">A requirements ↔ source loop</div>

<Notes>

None of this started as a product; each tool exists because I needed it. LabVIEW testing is still largely manual, so I want benchmarks an agent can run and verify. The monthly AI credit runs out and overage bills follow, so AI money should go only where judgement is needed: the requirements. And my own source needs requirements behind it, so I reverse-engineer it into specifications; from then on, requirements and source stay in one loop.

## Today: LabVIEW runs captured as evidence

<div class="b-journey"><span>Started</span><span class="on">Today</span><span>Next</span></div>

<div class="b-shot"><img src="/ecosystem-site/briefing/lba-frame-correlator.png" alt="The Frame Correlator in VS Code: CPU, RAM and disk activity for every captured frame of a LabVIEW launch, with a red line to scrub through the frames" /><p class="b-cap">Frame Correlator: CPU, RAM and disk for every frame of a LabVIEW launch; drag the red line to see the screen at that instant</p></div>

<div class="b-tiles b-four">
<div><Badge kind="working" /><strong>Corroboration Grid</strong>Independent machines must agree</div>
<div><Badge kind="working" /><strong>Capture a launch</strong>Covers icon-editor bug (CAR) tests</div>
<div><Badge kind="working" /><strong>Deterministic clock</strong>12 FPS, pairs with NI I/O Trace and DETT</div>
<div><Badge kind="working" /><strong>Mark the spot</strong>Click a frame to drop a marker</div>

<p class="b-banner">Break glass in case of emergency: the evidence is already captured</p>

<Notes>

Today, the [LabVIEW Benchmark Actor](https://github.com/svelderrainruiz/labview-benchmark-actor) turns LabVIEW runs into evidence. This is its Frame Correlator: CPU, RAM and disk for every frame of a LabVIEW launch, and dragging the red line shows the screen at that instant. Every machine with the extension is an actor with an abstract name, and a result counts only when independent actors agree. Capturing a LabVIEW launch lets a tester cover specific icon-editor CAR tests; a CAR is NI's bug-report number. The capture runs on a fixed clock of 12 frames per second, so its timings line up with NI I/O Trace and the Desktop Execution Trace Toolkit. And a human can click any frame to drop a marker. When something breaks, the evidence is already there.

</Notes>

## Actor Corroboration Grid: agreement before trust

<div class="b-journey"><span>Started</span><span class="on">Today</span><span>Next</span></div>

<div class="b-flow">
<div>Independent actors<small>different setups: Linux · Linux&nbsp;VM · Windows</small></div>
<div>Same results?<small>results, versions and verdicts are compared</small></div>
<div class="b-hi">At least 2 of 3 agree<small>the release passes; otherwise it is blocked and an issue opens</small></div>
</div>

<p class="b-banner">Today: 2 benchmarks reproduce the same outcome on 4 different setups</p>

<p class="b-foot">Each actor signs its results · 13 tools for AI agents · reference setup: Ubuntu 24.04 with LabVIEW 2026 Community Edition</p>

<Notes>

The Actor Corroboration Grid is how a result earns trust. Independent actors on different setups, for example Linux, a Linux VM and Windows, run the same checks and each signs its results. Their results, versions and verdicts are compared. If at least two of three agree, the release passes; otherwise it's blocked and an issue opens. There is no central results database. Today, two benchmarks reproduce the same outcome on four different setups (different operating systems, hardware and LabVIEW versions); only the timings differ, as you'd expect.

</Notes>

## Markers: a human points, the agent explains

<div class="b-journey"><span>Started</span><span class="on">Today</span><span>Next</span></div>

<div class="b-shot"><img src="/ecosystem-site/briefing/lba-markers.png" alt="Three markers, shown as orange triangles, dropped by a human on a captured LabVIEW launch in the Frame Correlator" /><p class="b-cap">Three markers (orange) dropped by a human on a captured LabVIEW launch; each one grabs the nearest frame</p></div>

<div class="b-flow">
<div><Badge kind="working" />A human marks the spot<small>where something looked wrong</small></div>
<div><Badge kind="progress" />An agent with no context<small>explains CPU · GPU · RAM · disk · screen in that range</small></div>
<div class="b-hi">Hybrid verification<small>human judgement + agent speed: faster troubleshooting</small></div>
</div>

<p class="b-next"><strong>Then:</strong> data tagging · an animated clip of the range · documentation updated by local agents</p>

<p class="b-foot">Agent side specified as LBA-REQ-105 · the wiki shows it as planned until an automated check proves it</p>

<Notes>

A human watching a benchmark knows where something looked wrong; an agent starts with no context at all. The marker is the hand-off: the human drops markers on the benchmark, and those markers tell the agent where to look. You're looking at three of them, and placing markers works today. Next, a local model reads exactly that range (CPU, GPU, RAM, disk and the screen, on one clock) and explains what happened. Human judgement says where to look, and the agent brings speed and evidence. That makes troubleshooting faster and turns verification and validation into an AI/human hybrid. The marked range then becomes a data tag, an animated clip and documentation that local agents update from the facts. Screen frames stay on the machine; only metadata goes to the agent. The agent side is in progress, specified as requirement 105.

</Notes>

## The local LLM loop

<div class="b-journey"><span>Started</span><span class="on">Today</span><span>Next</span></div>

<div class="b-flow">
<div>Hooks<small>every agent session is recorded automatically</small></div>
<div>Shared-schema database<small>cost, tokens, operator time, evidence</small></div>
<div>Local LLM<small>reads the facts, does the heavy lifting</small></div>
<div class="b-hi">Results back<small>the next agent starts with context ↺</small></div>
</div>

<div class="b-tiles b-three">
<div><Badge kind="working" /><strong>Hooks + shared database</strong>Record every agent session</div>
<div><Badge kind="progress" /><strong>Local drafting</strong>Local models draft documentation and rewrites</div>
<div><Badge kind="next" /><strong>Local test issues</strong>Local models take test issues; paid AI covers only requirements</div>
</div>

<p class="b-banner">Each task the local loop takes over saves paid AI credit</p>

<Notes>

This is the core of the plan. Hooks record every agent session automatically in a database with a shared schema: what it cost, the tokens, the operator's time and the evidence. The loop is designed so that a local model reads those facts and does the heavy lifting, and its results go back into the same database, so the next agent starts with context instead of from zero. Today the hooks and the shared database run on every session. In progress: local models drafting documentation and rewrites. Next: local models taking test issues, so paid AI covers only the requirements. Each task the local loop takes over saves paid AI credit; that's how the loop evolves towards zero overage.

</Notes>

## Security by governance, decisions by facts

<div class="b-cols">
<div class="b-box">

**Governance**

- Automated checks block a change when in doubt (180+ in the Benchmark Actor)
- Independent review; every requirement traced to a test

</div>
<div class="b-box">

**Facts**

- Every session's cost, tokens and operator time are on record
- So a change's cost can be estimated before it is made

</div>
</div>

<Notes>

Two things keep AI-assisted benchmarking honest. Governance: automated checks block a change when in doubt (the Benchmark Actor has more than 180), every change gets an independent review, and every requirement is traced to a test. Facts: every working session's cost, tokens and operator time are on record in a database I own. That lets me say "this change will cost X if you do it this way", and hand documentation upkeep to local AI based on facts, not guesses.

</Notes>
