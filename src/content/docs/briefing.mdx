## Every tool here was built to serve a real goal

- Manual LabVIEW testing is slow and hard to repeat
- AI agents help, but monthly credit runs out and overage bills follow
- Reusing a good idea means reverse-engineering someone's source
- **Goal:** AI credit only for requirements; local machines do the rest

<div class="b-flow">
<div>Three problems<small>manual tests · overage bills · reverse-engineering</small></div>
<div>Specification-driven design<small>AI-assisted coding against a spec</small></div>
<div class="b-hi">One goal<small>0 USD overage</small></div>
</div>

<Notes>

None of this started as a product. Each tool exists because I needed it. LabVIEW testing is still largely manual. The icon editor is a good example: someone clicks through scenarios and checks the results by eye. AI agents help a lot, but every month the credit runs out and an overage bill arrives. And when I like someone's idea, I usually have to reverse-engineer it from their source. So the goal is simple. Spend AI money only where real judgement is needed, which is the requirements, and let local machines do the heavy lifting. Specification-driven design is what gets me there: the AI codes against a specification, so the result stays robust as it grows.

</Notes>

## It started with seeing what changed in a LabVIEW VI

<div class="b-journey"><span class="on">Came from</span><span>Now</span><span>Going</span></div>

<div class="b-cols">
<div>

- Pick two Git versions of a VI; get a visual diff report
- Safety checks first, so it never uses the wrong LabVIEW
- A "what changed" summary right in Source Control
- Built-in MCP server: AI agents compare and summarise VIs themselves
- Open source (0BSD), version 1.36.1 on the VS Code Marketplace

</div>
<div>
<img src="https://raw.githubusercontent.com/LabVIEW-Community-CI-CD/vi-history-suite/main/docs/media/compare-flow.gif" alt="VI History Suite: right-click a VI, pick two revisions, and the comparison report opens" />
</div>
</div>

<Notes>

This is where we came from. LabVIEW code is graphical and saved in binary files, so Git can't show you what changed in a VI. [VI History Suite](https://github.com/LabVIEW-Community-CI-CD/vi-history-suite) fixes that inside VS Code. You pick two versions, it runs safety checks so it never uses the wrong LabVIEW, and you get a visual report you can share. It also has a built-in MCP server, which is the standard way AI agents call tools, so a Copilot agent can run comparisons and summarise them by itself. That taught me the lesson behind everything else: an agent is only as good as the facts you hand it.

</Notes>

## Now: LabVIEW benchmarking for CI/CD, where every machine is an actor

<div class="b-journey"><span>Came from</span><span class="on">Now</span><span>Going</span></div>

<div class="b-tiles">
<div><strong>Actor Corroboration Grid <Badge kind="working" /></strong>Independent actors must agree before a result counts</div>
<div><strong>Benchmark a launch <Badge kind="working" /></strong>Capture a LabVIEW launch; testers cover specific icon-editor CAR tests</div>
<div><strong>One deterministic clock <Badge kind="working" /></strong>Frame-locked at 12 FPS; timings pair with NI I/O Trace and DETT</div>
<div><strong>Tag a range <Badge kind="progress" /></strong>Two markers → a local vision model explains CPU, GPU, RAM and disk, with an animated clip</div>
</div>

<p class="b-banner">Break glass in case of emergency: the evidence is already captured.</p>

<Notes>

This is where we are now: the [LabVIEW Benchmark Actor](https://github.com/svelderrainruiz/labview-benchmark-actor), built for the LabVIEW CI/CD community. Every computer with the extension installed becomes an actor. Each actor has an abstract name, so there are no machine names and no central results database. It does four things for me. One, the Actor Corroboration Grid: a result counts only when a majority of independent actors in different environments agree. That's requirement 23 in the spec, and it's proven. Two, benchmarking: I capture a LabVIEW launch so a manual tester can cover specific icon-editor CAR tests (a CAR is NI's bug-report number). Three, one deterministic clock: capture is frame-locked at exactly 12 frames per second, so the timings can be paired with NI I/O Trace and the Desktop Execution Trace Toolkit. Four, data tagging, which is in progress: I drop two markers and a local vision model explains what happened to CPU, GPU, RAM and disk in that range, with an animated clip. And when something goes wrong, it's my break-glass tool, because the evidence is already captured.

</Notes>

It shouldn't arrive as a surprise on the bill.

## Specification-driven design: the spec tells your agent how to build it

<div class="b-journey"><span>Came from</span><span>Now</span><span class="on">Going</span></div>

<div class="b-chain">
<div>System requirements<small>SyRS</small></div>
<div>Software requirements<small>SRS</small></div>
<div>Tests</div>
<div>Design decisions</div>
<div>Results</div>
</div>

- Vibe-codeable source: the spec says how, and tests show it works
- Installer spec, published: 102 requirements · 58 test items
- Written so an agent given only the spec can rebuild it
- We compare requirements, not source

<Notes>

This is the idea I care about most: making the source "vibe-codeable". If you like something, you shouldn't have to reverse-engineer it. The specification tells your agent how to build it, and the tests show what it does. It's layered. System requirements, the SyRS, break down into software requirements, the SRS, and VI History Suite already has both. Each requirement is traced to a test and a design decision, following ISO/IEC/IEEE 29148, and every link is checked automatically. For example, the [installer specification](https://github.com/svelderrainruiz/ecosystem/wiki/Software-Requirements-Specification) is published with 102 requirements and 58 test items. It's written so that an agent given only the spec can reproduce the installer's behaviour. That's why we compare requirements, not source.

</Notes>

## Security by governance, decisions by facts

<div class="b-cols">
<div>

**Governance**

- Every change passes fail-closed gates before merge (180+ in LBA)
- Every requirement traces to a test and a design decision
- Independent review before anything is merged
- This site deploys only if its own check passes

</div>
<div>

**Facts**

- Every session records AI tokens, cost and operator time
- Kept in my own database: traceable, not estimated
- So I can say: "this change costs X if done this way"
- Docs upkeep goes to local AI; tasks are assigned from facts

</div>
</div>

<Notes>

Two things make AI-assisted coding robust here, and keep it safe and measurable. The first is governance. Every change passes fail-closed gates before it's merged, and the Benchmark Actor alone has more than 180 of them. Every requirement is traced to a test and a design decision, there's an independent review before anything is merged, and this site deploys only if its own check passes. The second is facts. Every working session records its AI tokens, its cost and the operator's time, in a database I own. That's what lets me say "this change will cost X if you do it this way". It also makes it easy to hand documentation upkeep to local AI, because tasks are assigned from facts, not guesses.

</Notes>

## The experiment: 0 USD in overage, starting 1 December 2026

<div class="b-timeline">
<div>Today<small>tools ready; overage not measured yet</small></div>
<div>1 Dec 2026<small>the experiment starts; overage is measured from here</small></div>
<div>Every month<small>the live trend, in relative figures</small></div>
</div>

- Primary goal: 0 USD on overage bills
- Reproducible either way: a failure can be reproduced, and so can success
- Results are live; run the same experiment on your own bill
- Secondary goal: automate icon-editor manual testing and open up research collaboration

<Notes>

Here's the experiment. My personal goal is zero dollars in overage. Getting there takes about 95 % fewer paid AI units a month than in November, through smaller contexts, cheaper models where they're good enough, and handing bulk work to local models ([the zero-overage programme](https://github.com/VITechnologies/projectbuddy/issues/375)). It starts on 1 December 2026; until then, overage isn't being measured. From then on the results are live, published as relative figures, so you'll see month by month whether the bill goes down, and you can run the same experiment on your own bill. It's reproducible either way: if it fails, you can reproduce the failure, and if it works, you can reproduce that too. The secondary goal is to automate manual testing on the icon editor and to open up research collaboration in which we compare requirements, not source.

</Notes>

## Principles of the Benchmark Actor

- Reproducibility over telemetry: the mesh coordinates runs, not a central results database
- Real data, no fakes: every capability is proven on a real capture behind a fail-closed gate
- The sandbox is your own isolated "golden" VM
- Hybrid labour: agents automate, and humans do the steps only a human can do
- Free and non-commercial
